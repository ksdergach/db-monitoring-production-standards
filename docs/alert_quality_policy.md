# Правила уведомлений для аномалий null_rate

**Статус: Предложение для согласования. В рабочем коде не реализовано.**

Результат [Issue #59](https://github.com/ksdergach/db-monitoring-production-standards/issues/59)
— спецификация дополнительного фильтра Telegram после Isolation Forest.
Пороги предварительные: команда должна согласовать их и проверить на реальных
эксплуатационных данных до отдельной реализации. Этот документ не меняет фильтр,
SQL, настройки, модель или существующие тесты.

## Проверенная исходная система

Проверка выполнена 23 октября 2026 года на свежем `master`
`992b9c7cfb1b39faea4e26ae410b37957262ddbd`, в отдельной ветке
`vds2/s20261023-131915-65bd1c`.

- В [collectors/per_project.py](../collectors/per_project.py)
  `_maybe_notify_anomalies()` выбирает последнюю точку с `is_anomaly=1`;
  `_passes_alert_quality_gate()` проверяет `abs(score) >= 0.05`, затем
  `abs(R − B_R) / B_R >= 0.10`. Значения по умолчанию взяты из
  [app/config.py](../app/config.py); локальные переопределения не исследованы.
- Если baseline `row_count` отсутствует или равен нулю либо нет текущего значения,
  после проверки score действующий фильтр пропускает уведомление. Сам фильтр
  не проверяет `is_anomaly` и знак score: отбор аномалий выполняет вызывающий код.
- Baseline в текущем SQL привязан к времени запуска, а не к времени события;
  запрос содержит только `ts >= since`, без верхней границы. Минимум — три
  записи, без проверки охвата и свежести. `null_rate` в фильтре не участвует.
- [ml/anomaly_detector.py](../ml/anomaly_detector.py) использует четыре признака:
  `row_count`, `null_rate`, их первые разности. Точки соединяются по совпадению
  временных отметок. Score — `decision_function`, а не вероятность инцидента.
- По [collectors/metrics_collector.py](../collectors/metrics_collector.py)
  табличный `null_rate` — среднее долей NULL по столбцам, округлённое до четырёх
  десятичных знаков; режимы `sample` и `approx` имеют отдельные ограничения.
  Правило ниже использует именно эту метрику, без изменения её семантики.

`a4aac2953bab9cdc72dd9b3f5f30d6d1ebc544f1`, base — указанный выше `master`.

### Наблюдение: текущий замер попадает в медиану

Комментарий `_baseline_median_row_count()` говорит об исключении аномальной точки,
однако SQL этого не обеспечивает. На временной SQLite с числовым столбцом `value`
выполнены извлечённые из `master` функции с прежними SQL и условиями, изолированными
от приложения; заменены только импорты, часы и адаптер соединения.

При `t = 2026-10-23T12:00:00+00:00` предыдущие значения 80, 100, 120 находятся
за 49, 25 и 1 час до события; текущее значение 112 записано в `t`.

| Расчёт | Медиана | Отклонение 112 | Решение при score = −0.2 |
| --- | ---: | ---: | --- |
| Только `[t−7 суток, t)` | 100 | 12% | Пропустить |
| Текущий SQL с включённой точкой `t` | 106 | 5.660377% | Отклонить |

Это наблюдение подтверждено запуском, но SQL в #59 **не исправляется**.

Спецификация ниже исключает такую утечку будущих данных.

## Предлагаемое правило Г

Пусть `R` — текущий `row_count`, `B_R` — его историческая медиана;
`N` — текущий `null_rate`, `B` — его историческая медиана. Все текущие значения
берутся строго в момент оцениваемой аномалии `t` для того же проекта и таблицы.

Для пригодного score и `is_anomaly = 1` сначала требуется `score <= −0.05`.
Затем достаточно одной подтверждённой ветви:

```text
row_pass  = B_R > 0 AND abs(R − B_R) / B_R >= 0.10
null_pass = N − B >= max(0.02, min(0.50 × B, 0.10))
allow     = is_anomaly = 1 AND score <= −0.05 AND (row_pass OR null_pass)
```

Формула применяется с правилами отсутствующих данных из следующего раздела.
Она допускает рост `null_rate` при стабильном числе строк; уменьшение `null_rate`
само по себе уведомление не разрешает. Изменение `row_count` учитывается в обе
стороны. Прохождение фильтра означает допуск к доставке: пригодность Telegram,
throttle, журнал попыток и ошибки отправки остаются отдельными этапами.

| Порог | Значение и единицы | Смысл |
| --- | --- | --- |
| Score | `−0.05`, безразмерный score IF | Равенство допускается; это не 5% вероятности |
| Row delta | `0.10`, относительная доля | Отклонение числа строк на 10% от положительной медианы |
| Нижний абсолютный рост NULL | `0.02`, доля от 0 до 1 | 2 процентных пункта (п.п.), не относительные 2% |
| Относительный рост NULL | `0.50 × B` | 50% от исторической доли NULL |
| Верхняя граница требуемого роста | `0.10`, доля | Не требуется более 10 п.п.; это не предел допустимого `N` |

Порог `h(B)` непрерывен и имеет три участка:

```text
0 <= B <= 0.04:    h(B) = 0.02
0.04 < B < 0.20:   h(B) = 0.50 × B
0.20 <= B <= 1:    h(B) = 0.10
```

При `B=0` нужен рост минимум до `N=0.02`, деления на ноль нет.
При `B=0.10` требуется `N>=0.15`; при `B=0.80` — `N>=0.90`.
При `B>0.90` порог недостижим для допустимого `N<=1`: высокий исходный уровень
NULL и небольшое дальнейшее ухудшение могут остаться без уведомления. Сам по себе
постоянно высокий уровень NULL этим правилом также не выявляется.

Сравнения включают равенство. Округлять дельту перед сравнением нельзя.
Для будущей реализации предлагается сравнивать десятичные значения сохранённых
метрик (например, `Decimal(str(value))`) без произвольного epsilon; относительную
ветвь строк можно проверить как `abs(R−B_R) >= 0.10 × B_R`.
Здесь воспроизводитель использует точную десятичную арифметику для Б/В/Г;
вариант А исполняет исходную арифметику `float`. Округление самой собираемой
метрики до четырёх знаков остаётся источником погрешности.

## История, пригодность данных и три состояния решения

Baseline рассчитывается **независимо для каждой метрики** по одному проекту и
таблице, в UTC, в полуоткрытом интервале `[t−7 суток, t)`.
Минимум три различных предыдущих timestamp; `max(ts)−min(ts) >= 24 часа`;
возраст последнего `t−max(ts) <= 24 часа`. Границы 7 суток и 24 часа включаются,
сама точка `t` и будущее исключаются. Если условий нет, baseline не определён;
это не свидетельство нормального состояния и не повод подставить ноль.

Timestamp нормализуется к UTC до группировки и сравнения; одинаковые мгновения
в разных часовых поясах — одна точка. Для воспроизведения все входы уже
нормализованы. Timestamp без определённого часового пояса/неразбираемый timestamp
считается ошибкой данных. Нельзя подменять время события текущими часами.

| Ситуация | Предлагаемое поведение |
| --- | --- |
| Нет истории, <3 разных timestamp, охват <24 часов, последний замер старше 24 часов | Ветвь получает состояние «недостаточно данных» |
| `B_R=0`, `R=0` | Row-ветвь не подтверждает изменение |
| `B_R=0`, `R>0` | Row-ветвь «недостаточно данных»: процент не определён; абсолютный порог строк нужно согласовать отдельно |
| `B=0` | Null-ветвь доступна, используется абсолютный минимум 2 п.п. |
| Текущая метрика отсутствует точно в `t` | Соответствующая ветвь «недостаточно данных»; ближайшее значение не подставляется |
| Дубли `(проект, таблица, метрика, timestamp)` с одинаковым значением | Одна точка, без увеличения веса/числа наблюдений |
| Дубли с конфликтующими значениями | Соответствующая ветвь «недостаточно данных», без произвольного выбора значения |
| NaN, бесконечность, отрицательное число строк, `null_rate` вне `[0,1]` | Ошибка данных, соответствующая ветвь «недостаточно данных»; не заменять нулём |
| Отсутствующий/нечисловой/нефинитный score или неизвестный флаг аномалии | «Недостаточно данных», обычное уведомление не допускается |
| `is_anomaly=0` или конечный `score>−0.05` | Отклонить до проверки дельт; положительный score не проходит |

Медиана — обычная невзвешенная медиана значений после дедупликации; для чётного
числа точек берётся среднее двух центральных. Обе метрики должны относиться к
одной сущности и сопоставимому способу сбора. Смена состава столбцов, режима
`full/sample/approx` или иной разрыв семантики требует отдельной проверки
пригодности истории; автоматическое смешивание такой истории не предлагается.

Итоговые состояния: **П** — пропустить, **О** — отклонить, **Д** — недостаточно
данных (включая некорректные данные). Для Б/В/Г используется одинаковая агрегация:

| Row-ветвь | Null-ветвь | Итог после проверки score |
| --- | --- | --- |
| Да | Любое состояние | П |
| Любое состояние | Да | П |
| Нет | Нет | О |
| Нет/Д | Д | Д |
| Д | Нет | Д |

Если одна ветвь подтверждена, отсутствие другой не блокирует событие, но признак
неполноты сохраняется. В состоянии Д обычное уведомление об аномалии не отправляется;
предлагается сохранить причину и результат оценки для диагностики, отдельно от
«нормально». Сроки эскалации проблем сбора и отдельный канал диагностики требуют
согласования; существующего автоматического механизма Д в рабочем фильтре нет.

## Четыре сравниваемых варианта

Точные формулы Б и В из утраченного исследования неизвестны. Для нового сравнения
они зафиксированы следующим образом; это самостоятельные, воспроизводимые
определения, а не утверждение об идентичности старой программе.

| Вариант | Ветвь строк | Ветвь NULL |
| --- | --- | --- |
| А — действующий | Текущий SQL, `abs(score)>=0.05`, дельта строк 10%; прежнее пропускание при отсутствии baseline/значения или нулевом baseline | Не используется |
| Б — простой OR | Предлагаемая история и дельта строк 10% | `abs(N−B)>=0.02`, в обе стороны |
| В — абсолютный AND относительный | Та же row-ветвь | `N−B>=0.02 AND N−B>=0.50×B` |
| Г — рекомендуемый | Та же row-ветвь | `N−B>=max(0.02,min(0.50×B,0.10))` |

В варианте В запись через умножение сохраняет определённость при `B=0`:
для положительного роста остаётся абсолютный минимум. Во всех Б/В/Г общий вход —
`is_anomaly=1 AND score<=−0.05`, общие правила Д описаны выше.
Для А в эксперимент включён реальный предварительный отбор `is_anomaly` вызывающим
кодом. Сам gate А с положительным score по модулю мог бы пройти, но сценарий 22
не доходит до него.

Таким образом, сравниваются полные политики допуска: Б/В/Г меняют и работу с
историей, и null-ветвь. На сценариях 01–23 история полная, постоянная и числовая;
включение текущего замера в А не меняет медиану. Влияние ошибки SQL изолировано
показано выше, а неизвестные данные — в 24–28.

### Фактические результаты нового запуска

Считаются только 01–23: 15 положительных и 8 отрицательных меток.

## Проверки и ограничения

Повторно выполнены на Python 3.12.3, без зависимостей приложения:

- 28 решений всех четырёх вариантов; подсчёты 23 размеченных сценариев.
- Исходные функции А из `master` в изоляции со SQLite; SQL-пример 100→106
  и фактическое отклонение уведомления. Это не полный интеграционный тест приложения.
- Точные границы ±10% строк, 2 п.п., относительных 50%, верхних 10 п.п.,
  точки излома `B=.04/.20`, score `−.05` и значения непосредственно ниже порогов.
- Нулевые базы, недостижимость при `B=.95`, независимое прохождение NULL при
  неопределённой row-ветви; неизвестный score, положительный score, флаг 0.
- Минимум три точки, охват ровно/меньше 24 часов, свежесть ровно/больше 24 часов,
  включение `t−7 суток`, исключение более старых, текущих и будущих точек,
  изоляция проекта/таблицы, одинаковые/конфликтующие дубли, отсутствующие текущие
  значения, NaN/бесконечность/выход за диапазон.

Markdown разобран и преобразован в HTML через `markdown-it-py 4.0.0`: девять
таблиц имеют согласованное число столбцов, относительные файловые ссылки существуют.
Все 28 строк решений и новая матрица подсчётов автоматически сверены с выводом
запущенного кода, извлечённого непосредственно из документа. Отображение в браузере
GitHub не проверялось; Mermaid в документе нет.
`pre-commit 4.6.2 run --files docs/alert_quality_policy.md --show-diff-on-failure`
прошёл все пять применимых hooks: пробелы, конец файла, конфликты, размер и
приватные ключи; остальные пропущены по типу файла.
`git diff --check` и проверка staged diff прошли. Тесты приложения pytest,
интеграционные проверки и линтеры Python проекта не запускались: изменён только
Markdown. Воспроизводитель расчётов выполнен отдельно; настройки зависимостей
проекта не изменены, средства проверки установлены в служебный каталог `.git`.

Воспроизводитель ниже предназначен для проектного эксперимента. Он не подключает
рабочие данные, не вызывает Telegram и не меняет приложение. У него нет задачи
реализовать весь будущий валидатор: нормализация разных часовых поясов, повреждённые
timestamp, смена режима/состава столбцов и обработка всех типов некорректных входов
описаны требованиями выше, но не проверены интеграционно.

Синтетические метки субъективны; распределение и частоты событий заданы вручную.
Нет доверительных интервалов, сезонности, задержек сбора, серии повторных алертов,
ошибок выборочной оценки NULL, реального трафика и оценки нагрузки. Score
некалиброван, не сопоставим с вероятностью, зависит от обучения/масштабирования.
Рост среднего NULL может скрывать проблему одного важного столбца; `sample` даёт
ошибку выборки, `approx` может отражать устаревшую статистику. Для пустой таблицы
доля NULL требует проверки смысла данных, а не автоматической подстановки 0.
Порогам нужна отдельная валидация по таблицам, объёмам и способам сбора.

`top_feature = argmax(abs(z))` показывает наиболее необычную координату относительно
StandardScaler. Это **не доказанная причина решения Isolation Forest** и не
причина инцидента: модель использует совместное расположение четырёх признаков.
В будущем сообщении допустимо показать дельты и основание прохождения gate,
но нельзя объявлять максимальный z вкладом/причинным объяснением IF.

"""Issue 59: stdlib-only, isolated SQL and decision-table experiment."""
import ast
import logging
import math
import sqlite3
from datetime import UTC, datetime, timedelta
from decimal import Decimal as D
from pathlib import Path
from statistics import median
from types import SimpleNamespace

T = datetime(2026, 10, 23, 12, tzinfo=UTC)


class Clock(datetime):
    @classmethod
    def now(cls, tz=None):
        return T


db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE metrics(project_id TEXT, table_name TEXT, metric_name TEXT, ts TEXT, value REAL)")
source = ast.parse(Path("collectors/per_project.py").read_text())
names = {"_passes_alert_quality_gate", "_baseline_median_row_count", "_latest_row_count_at"}
nodes = [n for n in source.body if isinstance(n, ast.FunctionDef) and n.name in names]
assert len(nodes) == 3
# Retain function bodies/SQL; replace only imports with injected stdlib adapters.
for node in nodes:
    node.body = [n for n in node.body if not isinstance(n, (ast.Import, ast.ImportFrom))]
env = dict(datetime=Clock, UTC=UTC, timedelta=timedelta, text=lambda s: s,
           get_engine=lambda: SimpleNamespace(connect=lambda: db),
           settings=SimpleNamespace(ANOMALY_NOTIFY_MIN_SCORE_MAGNITUDE=0.05,
                                    ANOMALY_NOTIFY_MIN_DELTA_RATIO=0.10),
           logger=logging.getLogger("issue59"))
exec(compile(ast.Module(body=nodes, type_ignores=[]), "isolated_master_gate", "exec"), env)


def put(metric, hours, value, project="p", table="q"):
    ts = (T - timedelta(hours=hours)).isoformat(timespec="seconds")
    db.execute("INSERT INTO metrics VALUES (?, ?, ?, ?, ?)",
               (project, table, metric, ts, str(value)))


def valid(value, metric):
    return value.is_finite() and value >= 0 and (metric != "null_rate" or value <= 1)


def baseline(metric):
    # Proposed event-time window, one value per distinct normalized timestamp.
    rows = db.execute("""SELECT ts, value FROM metrics
        WHERE project_id='p' AND table_name='q' AND metric_name=?
        AND ts >= ? AND ts < ?""", (metric, (T - timedelta(days=7)).isoformat(),
                                   T.isoformat())).fetchall()
    points = {}
    for ts, raw in rows:
        value = D(str(raw))
        if not valid(value, metric) or (ts in points and points[ts] != value):
            return None
        points[ts] = value
    times = sorted(datetime.fromisoformat(ts) for ts in points)
    if (len(times) < 3 or times[-1] - times[0] < timedelta(hours=24)
            or T - times[-1] > timedelta(hours=24)):
        return None
    return median(points.values())


def current(metric):
    rows = db.execute("""SELECT value FROM metrics WHERE project_id='p'
        AND table_name='q' AND metric_name=? AND ts=?""",
                      (metric, T.isoformat(timespec="seconds"))).fetchall()
    values = {D(str(r[0])) for r in rows}
    if len(values) != 1:
        return None
    value = values.pop()
    return value if valid(value, metric) else None


def decision(kind, score="-0.2", anomaly=1):
    score = D(score)
    if not score.is_finite():
        return "D"
    if not anomaly or score > D("-0.05"):
        return "O"
    br, r = baseline("row_count"), current("row_count")
    bn, n = baseline("null_rate"), current("null_rate")
    row = None if br is None or r is None else (
        abs(r - br) >= D("0.10") * br if br > 0 else (False if r == 0 else None))
    null = None
    if bn is not None and n is not None:
        delta = n - bn
        if kind == "B":
            null = abs(delta) >= D("0.02")
        elif kind == "C":
            null = delta >= max(D("0.02"), D("0.50") * bn)
        else:
            null = delta >= max(D("0.02"), min(D("0.50") * bn, D("0.10")))
    if row is True or null is True:
        return "P"
    return "D" if row is None or null is None else "O"


# id, historical row, current row, historical null, current null, desired, score, anomaly
# Desired labels are illustrative domain judgements, not measured incident truth.

def seed(br="100", r="100", bn=".10", n=".10", profile="01"):
    db.execute("DELETE FROM metrics")
    hours = [] if profile == "25" else [72, 48, 25] if profile == "27" else [49, 25, 1]
    for metric, value in [("row_count", br), ("null_rate", bn)]:
        for h in hours:
            put(metric, h, value)
    put("row_count", 0, r)
    put("null_rate", 1 / 60 if profile == "28" else 0, n)
    if profile == "26":
        put("row_count", 25, D(br) + 1)
        put("null_rate", 25, D(bn) + D(".01"))


results = []
for line in DATA.splitlines():
    if not line.strip():
        continue
    ident, br, r, bn, n, desired, score, anomaly = line.split()
    seed(br, r, bn, n, ident)
    # A includes the actual upstream anomaly selection, absent inside the gate itself.
    a = bool(int(anomaly)) and env["_passes_alert_quality_gate"](
        "q", {"score": float(score), "ts": T.isoformat(timespec="seconds")}, "p")
    outcomes = ["P" if a else "O"] + [decision(k, score, int(anomaly)) for k in "BCG"]
    results.append((ident, desired, outcomes))
    print(ident, desired, *outcomes)
assert len(results) == 28
for col, name in enumerate("ABCG"):
    counts = dict(TP=0, FP=0, FN=0, TN=0)
    for _, desired, outcomes in results:

for hours, expected in [([25, 1], None), ([23, 12, 1], None),
                        ([25, 24, 1], D(100)), ([48, 36, 24], D(100)),
                        ([49, 36, 24.0001], None), ([168, 25, 1], D(100)),

    put("row_count", 0, 999)
    put("row_count", -1, 999)
    put("row_count", 1, 999, project="other")
    put("row_count", 1, 999, table="other")
    assert baseline("row_count") == expected, hours

assert baseline("row_count") == D(100)

    seed(n=raw)
    assert decision("G") == "D", raw
seed()
db.execute("DELETE FROM metrics WHERE metric_name='row_count' AND ts=?", (T.isoformat(),))
assert decision("G") == "D"
print("Boundary/data checks: PASS")
