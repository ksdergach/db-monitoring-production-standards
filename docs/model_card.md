# Model Card: поиск аномалий в метриках таблиц DB Monitor

Дата сверки: **14 октября 2026 года**. Код: [`1023bf2`](https://github.com/ksdergach/db-monitoring-production-standards/tree/1023bf29abe174407b3fb8df7fd7c39f6c9230ed).
Карточка следует девяти разделам [Model Cards for Model Reporting (2019)](https://research.google/pubs/model-cards-for-model-reporting/).
Описан основной режим мониторинга проектов с подключениями; поведение старого режима `legacy` отдельно не рассматривается.

**Короткая сводка**

| Пункт | Описание |
|---|---|
| Назначение и задача | Помочь инженеру данных заметить необычное изменение агрегированных метрик таблицы: числа строк и доли пустых значений. Решение о причине и действиях принимает человек. |
| Модель | `StandardScaler` и `IsolationForest`, отдельная модель для каждой пары «проект, таблица». |
| Вход | Четыре признака: `row_count`, `null_rate`, `d_row_count`, `d_null_rate`; последние два — разности между соседними совпавшими по времени замерами. |
| Выход | Для каждой оценённой точки: `ts`, `score` и целочисленный `is_anomaly` (0 или 1). Оценки сохраняются в `anomaly_scores`. |
| Качество | На эталоне D1: 8 ложных отметок из 799 (около 1,0%). На D2: precision 100%, recall 80%. Это синтетическая проверка на обучающих данных, а не оценка качества в эксплуатации. |
| Ограничения | Нужны как минимум 201 согласованный замер для 200 строк признаков. Нет календарных признаков и разметки реальных инцидентов. Модель не видит содержимое отдельных строк. |
| Применение | Обучение при первой оценке без файла модели и каждую ночь в 04:00 по часам сервера. Параметры задаются через `ML_ANOMALY_*`. Уведомления дополнительно фильтруются. |

Условный пример одной строки входа после совмещения метрик и вычисления разностей:

```json
{"ts":"2026-01-05T00:15:00+00:00","row_count":1010.0,"null_rate":0.02,"d_row_count":10.0,"d_null_rate":0.0}
```

`ts` нужен для привязки результата, но в вектор признаков не входит. Для примера предыдущий замер имеет `row_count=1000` и `null_rate=0.02`.
Пример выхода ниже взят из [эталона D1](../tests/ml_golden/expected/anomaly_d1.json), а не рассчитан для условной строки выше:

```json
{"ts":"2026-01-05T00:15:00+00:00","score":0.101071,"is_anomaly":0}
```

## 1. Сведения о модели

- **Название:** детектор аномалий агрегированных метрик таблицы DB Monitor.
- **Тип:** обучение без учителя, Isolation Forest после стандартизации признаков.
- **Библиотека:** scikit-learn **1.6.1**, версия зафиксирована в [`poetry.lock`](../poetry.lock).
- **Владелец:** команда DB Monitor. Изменения и вопросы оформляются в репозитории проекта.
- **Реализация:** [`ml/anomaly_detector.py`](../ml/anomaly_detector.py), общие пути — [`ml/common.py`](../ml/common.py), настройки — [`ml/settings.py`](../ml/settings.py).
- **Идентификация версии:** коммит кода обучения и `trained_at` конкретного файла модели. Единого неизменного веса для всех таблиц нет. Сейчас файл хранит `model`, `scaler`, `trained_at`, `n_points`, но **не сохраняет коммит кода автоматически**: его нужно записывать отдельно при фиксации результата. Реестра версий и истории файлов пока нет.

Значения по умолчанию:

| Переменная | Значение | Назначение |
|---|---:|---|
| `ML_ANOMALY_N_ESTIMATORS` | 100 | Число деревьев |
| `ML_ANOMALY_CONTAMINATION` | 0.01 | Доля для настройки порога по обучающей выборке |
| `ML_ANOMALY_RANDOM_STATE` | 42 | Фиксация случайности обучения |
| `ML_ANOMALY_MIN_POINTS` | 200 | Минимум строк признаков для обучения |
| `ML_ANOMALY_TRAIN_WINDOW_DAYS` | 60 | Окно истории для обучения, дней |

`contamination` проверяется на диапазон `0 < x <= 0.5`. Настройки читаются из окружения и `.env`. Изменение параметров обучения применяется к заново обученной модели, а не переписывает уже сохранённый объект.

## 2. Назначение

Модель ищет необычные сочетания уровня и изменения двух метрик таблицы. Это позволяет обнаруживать последствия сбоев загрузки, дублирования импорта или роста пустых значений без ручного порога для каждой таблицы. Сигнал служит поводом для проверки инженером, владельцем данных или разработчиком.

В основном режиме [`collectors/per_project.py`](../collectors/per_project.py) после сбора без общего сбоя, если записаны метрики, оценивает последние 24 часа **независимо от Telegram-конфигурации проекта**. Сохраняются все оценки, включая нормальные точки. При отсутствии сохранённой модели `score_table` пробует обучить её; при нехватке истории оценка пропускается. Готовой модели достаточно двух согласованных замеров в окне оценки; минимум 200 строк признаков относится к обучению. Ошибки оценки, записи или уведомления одной таблицы не останавливают остальные и последующий расчёт дрейфа. Настройки Telegram проверяются только после сохранения оценок и отбора последней аномалии. Ночное переобучение пересчитывает 14 дней для проектов независимо от наличия Telegram.

Результат используется так:

- Обзор проекта показывает число аномалий за 7 дней; страница таблицы — карточку, список и метки на графике за 14 дней. API `GET /api/anomalies/<table>` позволяет выбрать диапазон; его значение по умолчанию — **7 дней**, а не 14.
- Разбор по признакам показывает значения, z-оценки и признак с наибольшим абсолютным отклонением. Это ориентир для диагностики, а не доказанная причина аномалии или точная атрибуция решения леса.
- Для Telegram из оценок выбирается последняя аномалия таблицы. При обычных условиях фильтр требует `abs(score) >= 0.05` и отклонение `row_count` от медианы за 7 дней не меньше 10%. Затем действуют ограничения частоты уведомлений.
- **Исключения фильтра:** если медиана не определена (меньше трёх точек), равна нулю либо отсутствует значение `row_count` в момент аномалии, проверка отклонения пропускается. Порог по `score` остаётся обязательным. Источники: `_passes_alert_quality_gate` и [`app/config.py`](../app/config.py).
- `POST /api/explain` предоставляет объяснение через NVIDIA NIM при наличии ключа, с возвратом к правилам при недоступности LLM. Объяснение нужно проверять по данным.

Не следует использовать модель для проверки корректности отдельных строк, установления причин инцидента, оценки людей или автоматического удаления/исправления данных. Метка не доказывает наличие ошибки, а отсутствие метки не гарантирует качество таблицы.

## 3. Факторы

| Фактор | Влияние и что учитывать |
|---|---|
| Размер и скорость роста таблицы | Норма определяется по истории конкретной таблицы. Быстрое изменение её режима может сделать старую модель неактуальной. |
| Частота и размер загрузок | Пакетные загрузки, очистки и легитимные массовые импорты могут выглядеть как аномалии. |
| День/ночь, будни/выходные | Календарь не входит в признаки. Повторяющиеся циклы могут отражаться в истории значений, но явного моделирования сезонности нет. |
| Интервал сбора | По умолчанию 15 минут, диапазон в форме подключения — 5–1440 минут. Разности признаков не нормируются на длительность интервала. |
| Пропуски метрик | Берутся только совпадающие timestamps двух метрик. Разность после пропуска относится к соседним доступным точкам, между которыми мог пройти больший срок. |
| История до инцидента | Массовые аномалии в обучающем окне могут повлиять на то, что модель считает нормой. |

Раздельных измерений качества по размеру таблиц, режимам загрузки, интервалам и календарным периодам пока нет. Их следует добавить при появлении размеченных эксплуатационных данных.

## 4. Метрики

Реальные инциденты не размечены, поэтому используются синтетические ряды с заданным нормальным поведением и известным всплеском:

- **Доля ложных срабатываний (FPR)** на D1: `FP / число нормальных точек`. Показывает шум детектора на стабильном росте.
- **Точность (precision)** на D2: `TP / (TP + FP)`. Показывает, какая доля отмеченных точек попала в заданный всплеск.
- **Полнота (recall)** на D2: `TP / (TP + FN)`. Показывает, какую долю десяти точек всплеска обнаружили.

Единица оценки — временная точка, а не целый инцидент или Telegram-сообщение. На D1 полнота по аномалиям не определена: положительных примеров нет.

`score` — результат `decision_function`, **не вероятность**. Отрицательное значение соответствует аномалии; флаг в коде получается через `predict == -1`, а публикуемый `score` округляется до шести знаков. Околонулевой округлённый score нужно читать вместе с флагом.

Фильтр уведомлений оценивается отдельно от модели: он может уменьшить и число ложных сообщений, и полноту. Эталонные тесты фиксируют результаты алгоритма при изменениях кода, но не измеряют качество каждого нового ночного обучения.

## 5. Данные для проверки

Источник — [`tests/ml_golden/datasets.py`](../tests/ml_golden/datasets.py). Оба ряда содержат 800 замеров с шагом 15 минут, начиная с `2026-01-05T00:00:00+00:00`, генератор `RandomState(42)`.

- **D1:** `row_count = 1000 + 10*i + N(0, 5)` (стандартное отклонение шума 5), `null_rate = 0.02`.
- **D2:** тот же ряд; в точках с индексами **600–609 включительно** `row_count` умножен на 3, а `null_rate` равен 0.5. Только эти десять точек считаются положительными примерами для расчёта полноты.

После вычисления разностей первая точка исключается: остаётся **799 оценок**. Эталоны: [`anomaly_d1.json`](../tests/ml_golden/expected/anomaly_d1.json) и [`anomaly_d2.json`](../tests/ml_golden/expected/anomaly_d2.json).

В [`test_golden.py`](../tests/ml_golden/test_golden.py) модель обучается отдельно на каждом ряду и оценивается на том же ряду. Подмена `get_metrics` возвращает весь синтетический набор независимо от аргумента окна. Следовательно, это **не отложенная выборка** и не точное воспроизведение временной фильтрации production-хранилища. В тестах данные не поступают из реальной БД, а файлы моделей направляются во временный каталог.

## 6. Данные для обучения

В эксплуатации для каждой таблицы проекта выбираются `row_count` и `null_rate` за последние 60 дней. Замеры совмещаются по времени и сортируются. Из последовательных согласованных точек получаются четыре признака:

```text
[row_count(t), null_rate(t), row_count(t)-row_count(t-1), null_rate(t)-null_rate(t-1)]
```

Первый замер не имеет предыдущего и исключается. Для обучения нужны не менее **200 строк признаков**, то есть минимум **201 согласованный замер**. `StandardScaler` обучается на этой же матрице, затем преобразованная матрица поступает в Isolation Forest. Разметка для обучения не требуется. При последующей оценке используется сохранённый scaler.

[`collectors/scheduler.py`](../collectors/scheduler.py) запускает `retrain_anomaly_detectors` каждую ночь в 04:00 по часовому поясу планировщика сервера. `retrain_all` обходит таблицы, а файл модели в `models/` перезаписывается; затем оценки пересчитываются за 14 дней. Ручной запуск: `make warmup-ml PROJECT_ID=<идентификатор проекта>`. Таблицы с недостаточной историей пропускаются.

## 7. Количественный анализ

Результаты пересчитаны **по сохранённым JSON-эталонам**, без переобучения и изменения эталонов:

| Показатель | D1: стабильный рост | D2: всплеск |
|---|---:|---:|
| Оценённых точек | 799 | 799 |
| Известных аномальных точек | 0 | 10 |
| Отмечено моделью | 8 | 8 |
| TP / FP / FN / TN | 0 / 8 / 0 / 791 | 8 / 0 / 2 / 789 |
| FPR | 8/799 = 1,0013% | 0/789 = 0% |
| Precision | 0/8 = 0% | 8/8 = 100% |
| Recall | Не определена | 8/10 = 80% |
| Отметок с `abs(score) >= 0.05` | 0 | 1 |

На D2 обнаружены индексы `600, 602, 603, 605, 606, 607, 608, 609`; пропущены `601` и `604`. На D1 ни одна из восьми ложных отметок не проходит даже первый порог фильтра уведомлений. Последняя строка таблицы **не является числом отправленных сообщений**: отправка зависит также от выбора последней аномалии, отклонения от медианы и ограничения частоты.

Доля отметок около 1% на обучающих данных связана с `contamination=0.01`. Это не доказательство FPR=1% на будущих данных. Значения precision/recall здесь относятся только к этому синтетическому всплеску; оценка на обучающей выборке оптимистична и не подтверждает качество в эксплуатации.

Для воспроизведения подсчёта из корня репозитория достаточно стандартной библиотеки Python:

```python
import json
from datetime import datetime, timedelta
from pathlib import Path

start = datetime.fromisoformat("2026-01-05T00:00:00+00:00")
for name in ("d1", "d2"):
    rows = json.loads(Path(f"tests/ml_golden/expected/anomaly_{name}.json").read_text())
    tp = fp = fn = tn = magnitude_pass = 0
    for row in rows:
        index = (datetime.fromisoformat(row["ts"]) - start) // timedelta(minutes=15)
        positive = name == "d2" and 600 <= index <= 609
        predicted = bool(row["is_anomaly"])
        tp += positive and predicted
        fp += not positive and predicted
        fn += positive and not predicted
        tn += not positive and not predicted
        magnitude_pass += predicted and abs(row["score"]) >= 0.05
    print(name, len(rows), {"TP": tp, "FP": fp, "FN": fn, "TN": tn}, magnitude_pass)
```

Дополнительные unit-проверки в [`test_anomaly_detector.py`](../tests/test_anomaly_detector.py): `test_score_table_low_fpr_on_stable_data` требует долю отметок меньше 5% на стабильном ряду; `test_score_table_detects_spike` требует хотя бы одну отметку в сценарии со всплеском. Последний тест сам по себе не проверяет, что отметка попала именно внутрь всплеска; это подтверждается приведённым выше анализом D2.

## 8. Этические соображения

На вход этого детектора поступают агрегаты таблицы, а не её строки или персональные записи. Демографические признаки не используются. При этом агрегированные объёмы, имена таблиц и время изменений могут быть конфиденциальной информацией об организации, поэтому нельзя автоматически считать их безопасными для публичного распространения.

Нужны разграничение доступа по проектам и осознанная настройка получателей Telegram. Отправка контекста во внешний LLM — отдельный шаг приложения, а не часть Isolation Forest; её допустимость следует оценивать отдельно. Ложные сигналы тратят время инженера, пропуски задерживают обнаружение проблемы. Результат модели и объяснение LLM должны помогать человеку проверять данные, а не заменять проверку.

## 9. Ограничения и рекомендации

- **Холодный старт.** При непрерывном сборе обеих метрик каждые 15 минут 201 замер покрывает 200 интервалов, то есть около **50 часов**. Это ориентир накопления истории, не гарантия готовности через двое суток: пропуски и ожидание следующего запуска обучения увеличат срок.
- **Редкий сбор.** Для 200 интервалов в окне 60 дней нужно примерно `200 * interval_minutes <= 60 * 24 * 60`, то есть интервал не больше **432 минут (7 ч 12 мин)**. При большем интервале регулярного сбора истории не хватит для стандартного минимума; точная граница зависит от включения концов окна. Значения, разрешённые формой подключения вплоть до 1440 минут, не гарантируют обучаемость с настройками по умолчанию.
- **Сезонность и пропуски.** Время суток и день недели не входят в признаки, разности не учитывают длительность пауз. При изменении режима загрузок нужно повторно оценить модель и настройки.
- **Порог.** Порог score равен нулю для данного обученного объекта; его положение задаётся через `contamination`. Около 1% относится к обучающим данным при стандартной настройке, а не к любой будущей выборке.
- **Нет реальной оценки качества.** Нужны журнал размеченных инцидентов и отложенная по времени выборка, разбор ошибок по таблицам и режимам сбора. Нельзя выдавать синтетические 100% precision за эксплуатационную гарантию.
- **Уведомления теряют часть сигналов.** Проверка изменения именно `row_count` может отсечь событие, выраженное только в `null_rate`. Telegram влияет только на доставку; оценки сохраняются и без него.
- **Жизненный цикл.** Сейчас нет проверки качества новой ночной модели перед заменой файла, реестра версий и штатного отката. Изменение настроек требует переобучения. Предлагаемые улучшения отслеживаются в [#42](https://github.com/ksdergach/db-monitoring-production-standards/issues/42).

**Связанные модели и методы.** [`ml/forecast.py`](../ml/forecast.py) прогнозирует метрики с Prophet, для коротких рядов использует линейную регрессию. [`ml/changepoint.py`](../ml/changepoint.py) ищет точки излома методом PELT, [`ml/drift.py`](../ml/drift.py) проверяет сдвиги распределений через PSI/KS; эти два метода не обучают сохраняемый предиктор аналогично Isolation Forest.
